| ACT4 | 🐞 **BUG — `CreateActor`/`CreateGroup` never clear a caller-supplied `id`, `created_at`, or (for Actor) `deleted` before writing the row, so a caller can forge a primary key, backdate the audit timestamp, or mint an already-soft-deleted row — the same server-owned-field-injection shape `mwanachama-backend-agency` already found and fixed fleet-wide as AG21/WK17, but never ported back to this repo, which is the very template agency's own CLAUDE.md says to copy.** `actor_impl.go`'s `CreateActor` only does `if act.CreatedAt == "" { act.CreatedAt = NowRFC3339() }` and never touches `act.ID`/`act.Deleted` before `gormstore.ActorToRow(act)`; `group_impl.go`'s `CreateGroup` has the identical `if g.CreatedAt == ""` idiom and never clears `g.ID` either. Both are reachable over real HTTP, not just the Go API: `routes/actor.go`'s `CreateActor` handler and `routes/group.go`'s `CreateGroup` handler both `readJSON` straight into the domain struct (which has `json:"id"`/`json:"created_at"`/`json:"deleted"` tags), with no narrower DTO in between. Demonstrated live through the real aggregator (`routes.ActorRoutes`/`routes.GroupRoutes` → a real `http.ServeMux` → `httptest.NewServer` → a real `http.Client`, not a direct manager call): `POST /actors` with body `{"id":"attacker-chosen-id","created_at":"1999-01-01T00:00:00Z","deleted":true,"display_name":"Ghost"}` returns **201** and echoes back **`id:"attacker-chosen-id"`, `created_at:"1999-01-01T00:00:00Z"`, `deleted:true`** verbatim. `GET /actors` (`ListActors`) correctly excludes the ghost row (it filters `deleted = false`), **but `GET /actors/attacker-chosen-id` (`GetActor`) still returns 200 with the same row, `deleted:true` intact** — `GetActor`'s query (`actor_impl.go`) carries no `deleted = false` filter the way `ListActors` does, so the row is fully readable by id despite being invisible to the roster; nothing else in this package's own code ever legitimately sets `Deleted = true` (no `DeleteActor` method exists at all), so today the *only* way a Deleted actor can ever exist is a caller choosing to POST one. `POST /groups` with `{"id":"attacker-group-id","hierarchy_id":"h1","level_id":"l1","name":"Ghost Group"}` likewise returns 201 with `id:"attacker-group-id"` honoured verbatim (a server-minted UUID never happens). Not separately demonstrated but sharing the identical code idiom (same `if X.CreatedAt == ""` guard, same un-cleared `ID` field) and therefore likely equally affected: `CreateGroupType`, `CreateHierarchy`, `CreateLevel` (none of the three have an HTTP route in this repo's `routes/` package to demonstrate through, so this is flagged as risk, not a separately confirmed finding, matching ACT3's own precedent for the Postgres-only half of its own finding). Pinned by `routes/createserverfields_test.go`'s `TestPinsACT4_CreateActorHonoursCallerSuppliedServerOwnedFields` and `TestPinsACT4_CreateGroupHonoursCallerSuppliedID`, both committed and passing — must go RED once ACT4's fix lands. `go build`/`go test ./...`/`go test -tags=integration ./...` all clean (no product code touched). |
| ACT3 | 🐞 **BUG — `NextCode` (`gormstore/codesequence.go`) reads the counter row then writes `next_number+1` with no CAS guard and no row lock, so two ordinary concurrent `Create<Type>` calls (`CreateActor`/`CreateGroup`/`CreateGroupType`/`CreateHierarchy`/`CreateLevel`/`CreateRoleKind`, everyday operations — a raced call is not a contrived scenario) can fail outright with a raw, unclassified database error. This corrects a prior sweep's own note (still on this board as ACT1's trailing observation) that called this gap "unreachable today" — that description belongs only to ACT1's *own* finding (a `Unique`-attribute race with no `Unique` attribute yet defined to race on); `NextCode` itself is called directly by `CreateActor`/`CreateGroup` on every single invocation and is fully reachable now.** `NextCode` does `SELECT ... WHERE entity_type = ?` (no `FOR UPDATE`/lock) to read `n`, computes `n+1` in Go, then `UPDATE ... SET next_number = <literal n+1> WHERE entity_type = ?` — no `WHERE next_number = ?` precondition, so nothing detects or serializes a second concurrent reader of the same `n`. Demonstrated directly against `UserManager.CreateActor` (`actor_impl.go:40` calls this same helper inside its own transaction), firing 2 goroutines concurrently per iteration across 30 iterations on a shared-cache multi-connection in-memory sqlite database (`file::memory:?cache=shared`, `SetMaxOpenConns(4)` — this repo's own single-connection `:memory:` test convention fully serializes each `CreateActor` call's whole transaction and cannot expose this race at all). Real output: **15/30 iterations (50%) had one of the two concurrent `CreateActor` calls fail** with `CreateActor: NextCode: database table is locked: database is deadlocked (6)` — a raw SQLite driver error propagated completely unwrapped to the caller, not any of this repo's own sentinels, for an operation (creating two unrelated Actors) that has no legitimate reason to fail. As with the identical shape independently found the same sweep in `mwanachama-backend-agency`'s own copy of this helper (filed there as AG35): demonstrated fact is the SQLite failure mode above; the more severe theoretical failure mode on Postgres (an unconditional `UPDATE` with no precondition letting a second writer silently proceed once the first commits, producing two rows sharing the same Code, e.g. two Actors both `"AC-5"`) was not demonstrated — this repo's own tests never stand up real Postgres — and is flagged as risk, not filed as a separately confirmed finding. Fix location: `gormstore/codesequence.go`'s `NextCode` — either a CAS write (`UPDATE ... SET next_number = ? WHERE entity_type = ? AND next_number = ?`, retried on `RowsAffected == 0`) or a row lock (`SELECT ... FOR UPDATE` on Postgres). | 📋 | Found 2026-09-21 by the fleet integration-test sweep, following up on ACT1's own "worth a second look when reachable" note by checking reachability directly — it already is. No committed pinning test — the probe needed a non-standard shared-cache multi-connection sqlite setup (`file::memory:?cache=shared`, `SetMaxOpenConns(4)`) diverging from this repo's own single-connection test convention, and its result (a 50% failure *rate*, not a deterministic reproduction) is a probe finding, not a stable regression-guard shape; the real output quoted above is the reproduction. Probe file (`zz_probe_nextcode_race_test.go`) deleted per the sweep's own rule against leaving a probe file behind. `go build`/`go test ./...`/`go test -tags=integration ./...` all still clean (no product code touched). |
