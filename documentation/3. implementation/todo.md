Both are reachable over real HTTP, not just the Go API: `routes/actor.go`'s `CreateActor` handler and `routes/group.go`'s `CreateGroup` handler both `readJSON` straight into the domain struct (which has `json:"id"`/`json:"created_at"`/`json:"deleted"` tags), with no narrower DTO in between. | ACT3 | 🐞 **BUG — `NextCode` (`gormstore/codesequence.go`) reads the counter row then writes `next_number+1` with no CAS guard and no row lock, so two ordinary concurrent `Create<Type>` calls (`CreateActor`/`CreateGroup`/`CreateGroupType`/`CreateHierarchy`/`CreateLevel`/`CreateRoleKind`, everyday operations — a raced call is not a contrived scenario) can fail outright with a raw, unclassified database error. This corrects a prior sweep's own note (still on this board as ACT1's trailing observation) that called this gap "unreachable today" — that description belongs only to ACT1's *own* finding (a `Unique`-attribute race with no `Unique` attribute yet defined to race on); `NextCode` itself is called directly by `CreateActor`/`CreateGroup` on every single invocation and is fully reachable now.** `NextCode` does `SELECT ... WHERE entity_type = ?` (no `FOR UPDATE`/lock) to read `n`, computes `n+1` in Go, then `UPDATE ... SET next_number = <literal n+1> WHERE entity_type = ?` — no `WHERE next_number = ?` precondition, so nothing detects or serializes a second concurrent reader of the same `n`. Demonstrated directly against `UserManager.CreateActor` (`actor_impl.go:40` calls this same helper inside its own transaction), firing 2 goroutines concurrently per iteration across 30 iterations on a shared-cache multi-connection in-memory sqlite database (`file::memory:?cache=shared`, `SetMaxOpenConns(4)` — this repo's own single-connection `:memory:` test convention fully serializes each `CreateActor` call's whole transaction and cannot expose this race at all). Real output: **15/30 iterations (50%) had one of the two concurrent `CreateActor` calls fail** with `CreateActor: NextCode: database table is locked: database is deadlocked (6)` — a raw SQLite driver error propagated completely unwrapped to the caller, not any of this repo's own sentinels, for an operation (creating two unrelated Actors) that has no legitimate reason to fail. As with the identical shape independently found the same sweep in `mwanachama-backend-agency`'s own copy of this helper (filed there as AG35): demonstrated fact is the SQLite failure mode above; the more severe theoretical failure mode on Postgres (an unconditional `UPDATE` with no precondition letting a second writer silently proceed once the first commits, producing two rows sharing the same Code, e.g. two Actors both `"AC-5"`) was not demonstrated — this repo's own tests never stand up real Postgres — and is flagged as risk, not filed as a separately confirmed finding. Fix location: `gormstore/codesequence.go`'s `NextCode` — either a CAS write (`UPDATE ... SET next_number = ? WHERE entity_type = ? AND next_number = ?`, retried on `RowsAffected == 0`) or a row lock (`SELECT ... FOR UPDATE` on Postgres). | 📋 | Found 2026-09-21 by the fleet integration-test sweep, following up on ACT1's own "worth a second look when reachable" note by checking reachability directly — it already is.
